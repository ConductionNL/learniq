# Proposal: rbac-declare-groups

## Summary
`lib/Settings/scholiq_register.json` (118 schemas) has never had FUNCTIONAL `authorization` configuration — but it is not empty of authorization-shaped content. 60 of the 118 schemas already carry keys that read exactly like working access-control rules: 20 carry `x-openregister-authorization` (e.g. `DossierNote`'s `create: ["admin","mentor","coordinator"]`), 40 carry `x-property-rbac`. Neither key is read by any code path in OpenRegister's `lib/` — confirmed against `Schema`, `PermissionHandler`, `OasService`, and `RbacGroupCollector` — while a positive control, `x-openregister-lifecycle`, IS read (3+ files). This was never simply "nobody declared authorization"; it is "60 declarations written under key names OpenRegister never reads, which look exactly like working access control in review." The practical effect, confirmed at the enforcement code itself (`PermissionHandler::hasGroupPermission()`): every one of the 118 schemas — including DossierNote, WellbeingCheckIn, BehaviourIncident, Attestation, LearnerProfile, and 16 other schemas holding sensitive personal data about minors — is READABLE by every authenticated Nextcloud user on the instance, with **no operator-side setting able to close that read path**. This change adds a register-level authorization cascade, schema-level blocks for the 21 sensitive-data schemas and the 21 catalogue/definitional schemas (13 shared-configuration + 8 course-content — see Scope), and the OAuth2 scope map that declares the canonical eight group ids the register depends on — so OpenRegister's `GroupProvisioner` creates the eight Nextcloud groups (`instructors`, `hr`, `compliance-officers`, `team-leads`, `learners`, `coordinators`, `guardians`, `administration-managers`) on the next import and RBAC starts actually gating access instead of merely appearing to. This change closes instance-wide open access on both the catalogue and the learner-attributed populations; it deliberately does NOT close per-learner scoping of learner-attributed records — a learner reading the course catalogue is unaffected by this change and always was in scope, only reading another learner's own grade/attendance/enrolment record stays closed pending a follow-up (see Open Questions). That distinction is load-bearing: an earlier draft of this change conflated the two and would have rendered the learner-facing product empty — corrected before this proposal was finalized.

## Motivation
The headline finding is not an absence — it is a decoy. 20 schemas already carry `x-openregister-authorization` and 40 carry `x-property-rbac`, both authored with content that *reads* like a working access-control rule, and both dead: grepping OpenRegister's `lib/` confirms neither key is read anywhere, while the closely-named `x-openregister-lifecycle` (a real, enforced extension key) IS read in 3+ files — proof the "OpenRegister reads `x-openregister-*` extension keys" assumption is half right, and the half that's wrong is the half that matters here. A reviewer skimming `DossierNote`'s JSON, or trusting its own description text ("Server-side x-property-rbac restricts every row..."), would reasonably conclude the schema already has row-level protection. It does not, and never has. This is not a hardening exercise on top of working access control — it is closing an open door that has looked, on casual inspection, like it was already closed.

Two further, independent lines of evidence confirm the door has no configuration-only lock, for the 58 schemas that carry no decoy key at all (and, for `read`, even the 60 that do — the decoy keys were never read, so they never closed anything):

- **Code-level**: `PermissionHandler::hasGroupPermission()` (~line 1292) branches explicitly on `empty($authorization) === true` with a comment reading "Default-OPEN behaviour preserved." There is a partial operator mitigation — `IAppConfig::getValueBool('openregister', 'enforce_default_closed')`, default `false` — but it only closes `DEFAULT_CLOSED_WRITE_ACTIONS = ['create', 'update', 'delete']`. **`read` is never in that list**; the docblock says so directly: "Reads remain default-open since `@PublicPage` is the OR-wide read model." So even a fully-hardened instance with the flag flipped on still serves every DossierNote, WellbeingCheckIn, and BehaviourIncident row to any authenticated user by GET. Declaring a real `authorization` block is the *only* way to close a read on an undeclared schema — there is no flag for it. OpenRegister already treats this as a known defect class: the same branch emits a one-shot-per-action `logger->warning()` ("DEPRECATION: schema without an authorization block grants {action} to any authenticated user...") the first time an undeclared schema/action pair is exercised — prior art that this gap has been announcing itself in the Nextcloud log for as long as these 118 schemas have existed, unread.
- **Live-measured**: `occ config:app:get openregister enforce_default_closed --default-value=UNSET` returns `UNSET` on localhost:8080 — the partial write mitigation isn't even enabled here, so today writes are open too, not just reads. `GET /cloud/groups` against the same instance found 28 existing groups and zero matching `/scholiq/i`, while a positive control (`decidesk-administrators`) confirms the query does return app-named groups when they exist — so the absence is real, not a query defect.

`lib/Service/DashboardRoleService.php` already assumes `scholiq-{role}` groups exist (`isInGroup($uid, 'scholiq-' . $role)` for compliance-officer/hr/manager/instructor) and has therefore never taken its role-aware branches, because those groups were never created. There is no code path in this app, past or present, that has ever provisioned a Scholiq access-control group. Every schema in the register — DossierNote (pupil-dossier notes), WellbeingCheckIn, BehaviourIncident, Attestation, and 17 more — has been readable, and (absent the unset flag) writable, by any authenticated user since the schema was written.

## Affected Projects
- [x] Project: `scholiq` — `lib/Settings/scholiq_register.json` gains a register-level `authorization` block, per-schema `authorization` blocks on 42 named schemas (21 sensitive-data + 21 catalogue/definitional), and a `components.securitySchemes.oauth2.flows.authorizationCode.scopes` map. No other project's files change.

## Scope

### In Scope
- A register-level `authorization` block on the `scholiq` register defining a named role (`configuration.roles`) and a staff-only cascade that governs every schema without its own `authorization` block (Tier 2 — **learner-attributed records**: what a specific person did, e.g. grades, attendance, enrolments — 76 schemas).
- Schema-level `authorization` blocks on the 21 Tier-1 (sensitive personal data) schemas, closed to named staff groups.
- Schema-level `authorization` blocks on the 21 Tier-3 (**catalogue/definitional**: what's on offer, not personal data about anyone) schemas, split across two write profiles: 13 shared-configuration schemas (write narrower than the cascade, excludes `instructors`/`hr`) and 8 course-content schemas — `Course`, `Lesson`, `Material`, `Programme`, `CurriculumPlan`, `Assignment`, `Assessment`, `ItemBank` — (write matches the cascade, includes `instructors` since they author this content). Read is `authenticated` (every logged-in user, `learners` included) on all 21 — deliberately WIDER than the Tier-2 cascade, not matching it; the two populations get different rules on purpose. This 8-schema course-content set is new relative to this change's first draft — see Risks.
- Deletion of the 20 existing `x-openregister-authorization` decoy keys, replacing the 9 that overlap with Tier 1/Tier 3 with real `authorization` blocks and removing the other 11 outright so Tier-2 schemas cleanly inherit the register cascade instead of carrying a dead, misleading key.
- The `components.securitySchemes.oauth2.flows.authorizationCode.scopes` map, hand-authored to carry all eight canonical group ids (four referenced by this change's authorization content, four declared scope-map-only to pre-provision them for the sibling `fix-dead-role-gates` change and later object-level-scoping work), per OpenRegister's "an exported configuration MUST declare the groups it depends on" requirement.
- Verification that importing the updated register actually provisions all eight Nextcloud groups (observable via `GET /cloud/groups`).

### Out of Scope
- Any PHP change, including `DashboardRoleService`'s `scholiq-{role}` group-name convention (still mismatched against the new free-form ids after this change — see Risk 2). Tracked as a separate change, `fix-dead-role-gates`.
- Any change to `src/manifest.json` `visibleIf` gates.
- The CI/Hydra gate work.
- Adding members to any of the eight groups once provisioned — provisioning is create-only by design (OpenRegister's `GroupProvisioner`); populating membership is an administrative act for a human operator, not a config change.
- Hand-authoring bespoke `authorization` blocks for all 118 schemas — the 76 Tier-2 (learner-attributed) schemas inherit the register cascade instead.
- A blanket group grant for `learners` on learner-attributed (Tier 2) data — deliberately excluded from the register cascade (see design.md's Residual Exposure section and this proposal's Open Questions). Per-learner (object-level, relation-scoped) access to THIS population is a separate, later change. (`learners` DOES get a wide read grant on the catalogue population — Tier 3, in scope, see above — the two are not the same thing.)
- Assigning any permission to `coordinators`, `guardians`, or `administration-managers` — declared (and provisioned) here so the sibling `fix-dead-role-gates` change has real groups to gate on, but not wired into any authorization rule by this change.

## Approach
Patch `lib/Settings/scholiq_register.json` only (declarative JSON, ADR-031 — no new PHP service). Follow OpenRegister's documented cascade: register-level `authorization` is the default for every schema that doesn't declare its own; schema-level `authorization` overrides the cascade entirely for that schema (most-specific-wins, no merging). Group ids are free-form, unprefixed, and sector-neutral by design — Scholiq is being reframed to serve both schools and companies (Learniq), so this change adopts the canonical eight-id vocabulary (`instructors`, `hr`, `compliance-officers`, `team-leads`, `learners`, `coordinators`, `guardians`, `administration-managers`, coordinated with the sibling `fix-dead-role-gates` change) rather than the app's dead, school-specific `scholiq-*` convention — see design.md Decision 2 for the full education/corporate label mapping. On the next configuration import, OpenRegister's `RbacGroupCollector` walks the document (register + schema + property authorization blocks, unioned with the scope map) and `GroupProvisioner` create-only-provisions any group id that doesn't already exist as a Nextcloud group — including the four ids declared only via the scope map. Full mechanism and per-tier authorization content are in design.md.

## New Dependencies
None. This change consumes OpenRegister's existing RBAC/group-provisioning machinery (`RbacGroupCollector`, `GroupProvisioner`, `DeclaredGroupInventoryService`) — already shipped, already a dependency (`^v0.2.14` per `x-openregister.openregister` in the register file).

## Impact
- `lib/Settings/scholiq_register.json` — the only file this change edits.
- Every one of the 118 schemas' effective RBAC posture changes at the next import: 21 Tier-1 schemas move from fully-open to a narrow named-group allow-list (no `learners`); 21 Tier-3 schemas move from fully-open to `read: authenticated` (wide, `learners` included) with staff-only write; 76 Tier-2 schemas move from fully-open to the staff-only register cascade (read AND write: staff roles only, no `learners`; delete: admin). The Tier-2/Tier-3 split is the load-bearing distinction — conflating them was this change's own draft error, corrected before finalizing (Risks).
- Eight new Nextcloud groups appear (empty, per OpenRegister's create-only provisioning contract) after the next import: `instructors`, `hr`, `compliance-officers`, `team-leads` (referenced by this change's authorization content) and `learners`, `coordinators`, `guardians`, `administration-managers` (declared via the scope map only — no authorization rule in this change grants any of the latter four anything).
- No API surface, route, or frontend code changes. The frontend already reads OAS `security` blocks for UI gating per OpenRegister's documented pattern (out of scope to verify frontend consumption in this change — see design.md Open Questions).

## Cross-Project Dependencies
Depends on OpenRegister `^v0.2.14` (already the declared floor) for `RbacGroupCollector` + `GroupProvisioner` + the register-authorization-cascade requirement family in `openregister/openspec/specs/rbac-scopes/spec.md`. No other apps-extra project is affected — group ids are free-form per OpenRegister's design, so if another app later declares `instructors` or `hr` it converges on the same Nextcloud group by design, not by accident; that is OpenRegister's documented behaviour, not a new coupling this change introduces.

## Risks

### Risk 1: Provisioned groups start empty and deny everyone until populated
**Severity:** High — **Mitigation:** This is OpenRegister's documented, deliberate contract (`GroupProvisioner` is create-only, never adds members) — not a defect introduced here, but it means this change alone does not restore anyone's access; it only makes the access boundary real and visible. `DeclaredGroupInventoryService` already exposes the empty-member state so an administrator sees the actionable rows immediately after import rather than discovering the lockout via a support ticket. The rollout task explicitly calls out "populate the four staff groups" (`instructors`/`hr`/`compliance-officers`/`team-leads`) as the immediate follow-up action for a human administrator, not a code task — the other four (`learners`/`coordinators`/`guardians`/`administration-managers`) are pre-provisioned for later changes and have no permission attached yet regardless of membership.

### Risk 2: DashboardRoleService's `scholiq-{role}` group convention still won't match after this change
**Severity:** Medium — **Mitigation:** `DashboardRoleService::resolvePrimaryRole()` tests `isInGroup($uid, 'scholiq-' . $role)` for `compliance-officer`/`hr`/`manager`/`instructor` (singular, prefixed). This change provisions the canonical eight ids (plural where applicable, unprefixed, sector-neutral — see design.md Decision 2) per OpenRegister's "group ids are free-form and SHALL NOT be prefixed" rule. The mismatch is real and pre-existing — `DashboardRoleService`'s branches have never fired regardless of this change — and is now resolved AT THE VOCABULARY LEVEL: the `fix-dead-role-gates` change's own group ids were coordinated against this change's, so both converge on the same eight rather than reproducing the mismatch under new names. The PHP reconciliation itself remains that change's job, referenced here so nobody mistakes this change for having done it.

### Risk 3: Tier-1 profile assignments are a judgment call, not a literal transcription of any existing document
**Severity:** Low — **Mitigation:** design.md names all 21 Tier-1 schemas individually against one of four narrow authorization profiles and states the rationale per profile. Any single schema's assignment is easy to move to a different profile in a follow-up PR — the risk is a support ticket ("my role can't see X"), not a security hole, because every profile is narrower than the current fully-open default.

### Risk 4: Catalogue-vs-learner-attributed misclassification (the mistake this change already made once)
**Severity:** Low — **Mitigation:** An earlier draft of this change applied one staff-only rule to all of Tier 2, including course-content schemas (`Course`, `Lesson`, `Material`, `Programme`, `CurriculumPlan`) — which would have rendered the learner-facing product empty, since learners never read their own course list without an object-owner match (instructors author courses, not learners). Caught and corrected before this proposal was finalized (design.md Decision 4). The residual version of this risk is narrower: a schema mis-tiered the OTHER way (classified catalogue when it actually carries learner-attributed data) would over-grant `learners` a read they shouldn't have. Mitigation is the same shape as Risk 3 — all 21 Tier-3 schemas are named individually in REQ-003, reviewable one at a time, plus an explicit approximation flag on `Assignment`/`Assessment`/`ItemBank` (design.md) where a property-level result field is the most plausible place this could still be wrong.

### Risk 5: `authenticated` is provisioned as a real, empty, permanently-inert Nextcloud group
**Severity:** Low — **Mitigation:** A side effect of Tier 3's `read: ["authenticated"]` — `RbacGroupCollector::RESERVED_PRINCIPALS` doesn't yet include `authenticated` alongside `admin`/`public`, even though `PermissionHandler`/`MagicRbacHandler` treat it as an equally pure pseudo-group. The group will exist, have zero members, and membership in it will never be tested by anything — cosmetic, not a security gap, but capable of confusing an administrator who finds it in the group-admin UI. Verified explicitly (Task 6) rather than silently tolerated; the real fix is an upstream one-line addition to OpenRegister's `RESERVED_PRINCIPALS`, flagged as a follow-up ask (design.md Decision 7), not worked around in this app's config.

## Rollback Strategy
Revert `lib/Settings/scholiq_register.json` to its pre-change committed state and re-import. Because OpenRegister's schema/register authorization is evaluated live from the stored `Schema`/`Register` entity on every request (no cache invalidation lag beyond the documented per-request cache), reverting the source file and re-importing restores full-CRUD-for-all-authenticated-users immediately. The eight provisioned Nextcloud groups are NOT deleted by a rollback (`GroupProvisioner` never deletes) — an administrator who wants them gone removes them manually via Nextcloud's group admin UI; leaving them in place is harmless (an empty, unreferenced group grants nobody anything).

## Open Questions
- **Per-learner scoping is explicitly NOT closed by this change, and that is deliberate — but it applies to ONE of two populations, not all schemas.** This change closes instance-wide open access on both populations it defines. For the catalogue population (Tier 3 — courses, lessons, materials, programmes: what's on offer, not personal data about anyone), `learners` gets exactly the wide read they need, same as every other authenticated user — that population is fully closed by this change, nothing deferred. For the learner-attributed population (Tier 2 — grades, attendance, enrolments: what a specific person did), read/write becomes staff-only (or the schema's own object-owner), and a learner still cannot distinguish "my own grade" from "any other learner's grade" through any mechanism this change provides, because a Nextcloud group grant is necessarily blanket (member sees every row, not just their own). Closing THAT needs object-level conditional scopes (`{group, match}` rules — the mechanism already exists in OpenRegister, see design.md's Residual Exposure section) and is owned by the later administrations change, not this one. Do not read this change as "RBAC done," and do not read "RBAC done" as "the learner-facing product is broken" either — an earlier draft of this change conflated the two populations and would have done exactly that (design.md Decision 4); the corrected scope is narrower and more precise than "learners lose access to Tier 2." Per-learner self-access to their OWN learner-attributed records is a follow-up, tracked as this change's most consequential open item.
- Whether the frontend (Vue/Pinia stores) currently reads OAS `security` blocks to conditionally hide create/edit UI for Tier-1 schemas, and if not, whether users who lack write access will see a create button that then 403s. Deferred to a follow-up UX-focused change — this change's scope is the authorization data model only (see DEFERRED_QUESTIONS in the final report).
